## Goals / Non-Goals

**Goals:**
- Represent every piece needed to render the site as a true Figma Component — scoped by design-system completeness (does a human ever need to style/reuse this?), not by whether it happens to be a `components/*.js` file today.
- Upgrade every pushed component from a flat frame to a true, instanceable Figma Component, with variants for real CSS states/breakpoints (not viewport-by-viewport duplication) and component properties for variable content.
- Establish and document the instance-override discipline (what safely varies per-instance vs. what requires a new variant vs. what's a genuine one-off) and a hard redesign-proofing rule (token/style references only, auto-layout throughout).
- Cover the full token file as Figma Variables (with modes for fluid values and for typeface exploration) and Text Styles, documented on a Foundations page.
- Structure the file for cross-project reuse (Core/Theme split) and for managing speculative/unused work (Ideas page + status field) from the start, not retrofitted later.
- Assemble a whole-page Desktop and Mobile reference from real instances, for visual QA and reuse-proofing — separate from the push/pull loop.
- Sketch three real interactions using Figma's native prototyping primitives, and define how pulled interaction data gets used (translation input, not codegen).
- Keep the whole thing non-destructive: nothing here changes the deployed site without explicit, separate approval, matching the archived change's proven constraint.

**Non-Goals:**
- Redesigning the live site's visuals. Still requires separate, explicit approval before touching the live site, same as the archived change.
- Making the pushed frames pixel-identical to the live site's exact font. `PPRadioGrotesk` isn't available to this MCP connection — Inter is accepted as the stand-in, documented as a known gap, not solved here.
- Automating the resync trigger. Resync remains pull-on-request only.
- Modeling continuous fluid (`clamp()`) resizing in Figma. Figma variables hold static values; two-mode endpoints (Desktop/Mobile) plus a documented formula is the ceiling here, not true fluid interpolation.
- Generating working application code from Figma prototype interactions. Reactions are read as structured intent for a human/Claude to hand-translate, per `figma-interaction-sketch`.
- Deciding the `content.md` schema for per-project media, or which content surfaces (web/CV/detail-page) show what. Both are real content-model decisions for the owner — this change documents a Figma-side convention ahead of them (see Open Questions) without making the call itself.
- Actually publishing a Figma Team Library. The current Starter plan doesn't support it (verified); the Core/Theme page split is built so publishing becomes trivial later, not attempted now.

## Decisions

**Variant axes: `state` and `breakpoint`, not a `kind` axis for table-row content differences.** `recordRow` actually varies by table kind too (`COL_LABELS` shows commercial/event/education tables omit awards/support, use different column labels) — but that's presence/absence of optional detail rows, not a different visual treatment. Modeled as per-instance layer visibility (Figma instances can hide/show child layers per-instance) rather than a `kind` variant axis, so the variant matrix stays small (`state` × `breakpoint` = 4 combinations) instead of exploding across every table kind. Alternative considered: a `kind` variant per table type — rejected, since it would multiply the variant count for a difference that's really about optional-row visibility, which Figma already has a native per-instance mechanism for.

**Nested composition mirrors the JS call graph.** `recordRow.js` calls `Components.statusDot()` and `Components.entityBlock()`/`splitEntityCell()` to build part of its output; the Figma-side `recordRow` Component nests instances of `statusDot`'s and `entityBlock`'s own Components in the same structural position, rather than flattening everything into one frame's layers (as the proof-of-loop push did). This keeps a real edit-once-propagate-everywhere relationship, and keeps the Figma structure legible against the code it represents — matches the "reusable, scalable" methodology goal directly.

**Reference content: 3 real records, not lorem ipsum.** `VYOLA CYANA` (shortest), `IT WAS RAINING` (medium, already pushed once as the proof-of-loop content), `MAILIN` (longest — the festivals/awards lists are the actual stress case for wrapping and the `{wip}` split). Chosen specifically because this site's layout risk is driven by real content-length variance the owner already has, not hypothetical copy-fitting lorem ipsum would need to fake.

**Fluid tokens → two Figma variable modes (`Desktop`/`Mobile`) holding each `clamp()`'s endpoints, formula in the variable description.** Figma has no `clamp()`-equivalent; the honest representation is the two extremes plus a written note of the actual formula, not a fabricated third "average" value. Alternative considered: picking one static value per token (e.g. always the clamp's preferred/middle term) — rejected, since it silently discards exactly the responsive information the token exists to carry, and gives no way to check either extreme visually.

**Text Styles, not just variables, for typography.** A Figma Variable holds one scalar (a size, a spacing value); a Text Style bundles font family/size/line-height/letter-spacing/case into one reusable, pickable unit — the actual Figma-native equivalent of a CSS heading/paragraph class. Both are used together: Text Styles reference the token variables for their scalar values, so changing a token still cascades into every Text Style built on it.

**Whole-page assembly is a separate artifact from the push/pull loop, built from instances only.** Editing an instance inside the whole-page assembly must not be mistaken for editing the component's source — resync stays scoped to each component's own mapped node in `figma-map.json`, never to an instance found elsewhere in the file. This is a deliberate boundary (see `figma-site-assembly`'s "does not drive push/pull resync" requirement) to keep the resync's blast radius exactly as narrow as the archived change already established.

**Full-coverage scope, not code-reuse scope.** The first draft of this change scoped "what becomes a Figma Component" by whether a `components/*.js` file already existed for it — wrong test. A design system needs every visually distinct, stylable piece represented (toolbar, hero, hide/show button, dark-mode button, scroll-CTA, an underline-mark atom, images), whether or not the code extracts it as a reusable function. Code-side reuse and design-side reuse are different axes; conflating them was the error. `components/toolbar.js`/`hero.js` still aren't warranted (no repeated pattern in the render code — see Non-Goals), but `toolbar`/`hero` Figma Components are.

**Content via component properties, not a fixed set of static pushes.** Real content alone (the original plan) can't stress-test lengths the owner doesn't yet have in `content.md`; lorem ipsum alone would hide the actual risk (this site's layout problems are driven by real content-length variance — long festival lists, the `{wip}` split, the "—" placeholder collapse). The correct mechanism is Figma's native one: TEXT/BOOLEAN component properties on each content-sensitive component, so any instance can carry real content, a synthetic stress string, or a controlled empty-state (`hasFestivals: false`) — all without detaching from the master. Real records ship as the defaults; synthetic short/medium/heavy presets live alongside as an explicit stress-testing set, reusable across every content-sensitive component, not rebuilt per component.

**Instance-override discipline, stated as a working rule, not left implicit.** A Figma instance stays linked to its master for everything it hasn't explicitly overridden; only an explicit override (a component property value, a swapped nested instance, a toggled visibility) is instance-local, and `Detach Instance` is the only thing that permanently severs the link. Rule going forward: anything expected to vary per-instance becomes a component property; a manual override is reserved for genuine one-offs; detaching is treated as a last resort worth flagging when it happens, not a normal workflow step. This is what makes "edit the template, it ripples everywhere, but this one instance can still differ slightly" both possible and safe.

**Redesign-proofing: tokens/styles only, auto-layout throughout — no exceptions.** The site's real strength is that `content.md` is the only thing that changes for new content, and rendering is fully automatic; the design system needs the equivalent property for *visual* changes. Concretely: no component may bind a fill, size, or spacing value to a literal when a token exists for it, and every container uses auto-layout rather than fixed `x`/`y` placement, so a redesign (new spacing scale, new type ramp) reflows instead of requiring every node to be manually re-placed. Treated as a hard rule rather than a preference, since a single hard-coded exception is exactly the kind of thing that quietly reappears and undermines the whole point.

**Cross-project reuse: Core/Theme page split now; published library later, if ever.** The target architecture is a published Team Library (generic, theme-agnostic pieces, consumed by other project files via the Assets panel) — but the Starter plan can't publish libraries (verified live via web search, not assumed; see Context). Rather than block on a plan upgrade the owner hasn't committed to, the file is structured today with the split already in place: a "Core" page holding only generic, unbranded atoms/molecules with no this-site-specific token *values*, separate from a "Theme — EstebanCuenca CV" page holding this project's real values/content. If publishing ever becomes available, "Core" converts to a library with near-zero rework; if not, it's still a clean, literally-copy-pasteable starting point for the next project. Alternative considered: build everything in one undifferentiated file and worry about extraction later — rejected as the actual shortcut-to-regret here, since untangling theme-specific values from generic structure after the fact is real, avoidable rework.

**Speculative/unused components get a real home and a status, not silent clutter.** A dedicated "Ideas / Unused" page, separate from Foundations/Components/Site-assembly, holds anything built but not (yet) adopted — including a **"Project Detail" template**, built ahead of the content-surface decision (see Open Questions) as a design exploration, not a real target. Every `components/figma-map.json` entry gains a `status` field (`active`/`idea`/`deprecated`/`speculative`); only `"active"` entries are ever treated as resync targets, so an idea-stage node can never be mistaken for one with a real `components/*.js` counterpart to pull into.

**Interactivity: Figma's native prototyping primitives, chosen for their closest real analog.** Dark/light toggle maps unusually well onto Figma's own "Set variable mode" prototype action, since the site's actual mechanism *is* a token-value swap (`html.dark` overriding `--ink`/`--mid`/`--bg`) — this is one of the few cases where Figma's interaction model and the site's real implementation share the same underlying idea, not just a visual approximation. Section hide/show and row hover are visual approximations only (Smart Animate, hover trigger) — the site's real behavior (`toggleSection`, localStorage persistence) has no Figma equivalent and isn't claimed to.

## Risks / Trade-offs

- [Converting the existing flat-frame `recordRow` push to a true Component is a breaking structural change to what's already in the Figma file] → it's a scratch/proof file the owner knows is disposable-and-rebuildable (`EC Design Sync — Scratch`); confirm before deleting/restructuring it in case the owner made manual edits there they want preserved first.
- [Variant matrix could still grow unmanageably if more axes get added later (e.g. per-status dot color, per-table-kind visibility) without discipline] → the "per-instance visibility over new variant axis" decision above sets the pattern; new components should default to it before proposing a new axis.
- [Figma Variable modes for fluid tokens is a lossy representation — someone could mistake the two endpoints for the whole fluid range] → every such variable's description explicitly states the real `clamp()` formula, so the gap is documented at the point someone would look, not just in this design doc.
- [PPRadioGrotesk remains unavailable throughout, so no pushed frame is ever font-faithful] → documented as an accepted, known gap per component push (matches how the archived change already handled it for the one component pushed so far), not something this change attempts to fix.
- [Reading Figma `reactions` during a future resync could be mistaken for "the interaction is now implemented"] → `figma-interaction-sketch`'s spec explicitly requires reporting reactions as translation input, and requires reporting a gap when no code equivalent exists, rather than silently treating a read as a done implementation.
- **RESOLVED** — [The Starter plan can't publish a library, so the Core/Theme split's cross-project payoff doesn't land until/unless the owner upgrades] → `EstebanCuenca` is now Professional (see Context), so publishing "Core" as a real Team Library is now actually available, not just a someday-maybe. The split still stands regardless — it's good structure either way — but publishing it is now worth doing rather than only theorizing about.
- [A component property matrix (content fields × state × breakpoint) could grow unmanageably per component] → the "per-instance visibility/property over new variant axis" precedent from the archived phase's `kind` decision applies here too; component properties handle content variation, variant axes stay reserved for genuinely distinct visual structures (state, breakpoint).
- [The "Ideas/Unused" page and `status` field could silently accumulate untracked cruft if not maintained] → same discipline as `figma-map.json`'s existing "every component file gets an entry" rule (from the archived change): every Figma node placed on the Ideas page gets a mapping entry with its status, so nothing is invisible to the map even when it's explicitly not active.
- **RESOLVED** (`EstebanCuenca` upgraded to Professional/Full mid-change — see Context) — [The Starter plan enforces an MCP tool-call rate limit of **20 calls per month, flat, regardless of seat** (confirmed via Figma's own rate-limits doc — View/Collab and Dev/Full seats share the same 20/month ceiling on Starter; per-day/per-minute limits only begin at Professional) — a sitemap-building session hit it mid-fix, interrupting a multi-call layout correction] → this is a distinct, more severe constraint than the no-library-publishing limitation (same plan, different restriction), and a real threat to this change's phased methodology: `figma-use`'s own best practice (small increments, verify after each step) assumes a call budget this plan doesn't have — one phase could plausibly need 15-30 calls on its own. `create_new_file`/`whoami` are exempt; `use_figma` (this change's primary tool, read and write scripts alike) is not. Mitigation is a real trade-off the owner needs to weigh, not something to default past silently: either accept a heavily-batched cadence (fewer, larger `use_figma` scripts per phase, less incremental verification, higher risk of harder-to-debug failures) or upgrade the plan (Professional resolves this **and** the library-publishing limitation together). Work within a phase should still be resumable/idempotent (check for an existing node before recreating it) so hitting the limit mid-phase leaves a recoverable, not corrupted, state.

## Post-Phase-5 hardening: real reference viewports and full size-token binding

Prompted by the owner explicitly asking the assembly to "respect max sizes, boundaries, padding" for real design decisions — this surfaced that the original Desktop/Mobile mode values, while internally documented as "the clamp's endpoints," weren't tied to any *specific, real* viewport width, and that font-size (unlike color) had never been systematically bound to variables at all.

**Reference viewports, computed not guessed**: Desktop = **1600px** — verified by computing every desktop-scale clamp at that width; all of them (`nav-size`, `body-size`, `bio-size`, `pad-x`, `space-xl/lg/md/sm`, `#cv-name`) are simultaneously saturated to their max exactly at/by 1600px, making it the smallest width at which the existing "Desktop = clamp max" values are actually true. Mobile = **390px** (a standard modern phone width, comfortably inside the real `≤768px` breakpoint) — computing each token's real `clamp()` value at exactly 390px found that `pad-x`/`space-*` were already correct (their vw-component floors out below 390px, coincidentally matching what was already stored), but `nav-size`/`body-size`/`bio-size`/`#cv-name`'s dedicated mobile-media-query clamps were NOT yet saturated at 390px — the stored Mobile-mode values (each clamp's max) were wrong, overstating real mobile sizes. Corrected to the actual computed values (e.g. `nav-size` mobile: 14.82, not 17).

**Two new variables added**: `ent-title-size`/`ent-sub-size` (Desktop: em-relative to `body-size`, since the real CSS is `1.05em`/`.92em` in that context; Mobile: their own dedicated clamps, evaluated at 390px) — `recordRow`'s entity title/sub previously had no token backing `entityBlock`'s master (color was bound, size wasn't).

**Found and fixed: `recordRow`'s label/value text (role/premiere/festivals/awards) had never been bound to `nav-size`/`body-size` at all** — literal `fontSize` numbers were set at Phase 3 build time, matching the values *then*, but with no live connection to the token system. Bound all of them (all 4 variants) after the fact. Also found one direct bug: the hero Mobile name text had `fontSize` explicitly set as a literal (`= 56`) *after* applying its Text Style — a literal always overrides a style's binding, so despite looking correctly styled, it was silently disconnected from `name-size` entirely. Fixed by re-binding.

**The other real finding, more structural**: none of this mattered until an explicit Sizes-collection mode was set — with no override anywhere, every bound node was silently resolving to the collection's default mode (Desktop) regardless of which breakpoint variant it lived in. Fixed by calling `setExplicitVariableModeForCollection` on each assembly's page-level frame (Mobile page → Mobile mode, Desktop page → Desktop mode explicitly), which cascades to every descendant that doesn't set its own override. This is the mechanism that makes "build once, bind to tokens" actually branch correctly by breakpoint — worth calling out clearly since the earlier phases established the binding discipline but never verified this specific plumbing.

Final state, verified programmatically (not eyeballed): 0 of 297 text nodes have an unbound `fontSize` across the whole Theme page — the same rigor already held for color now holds for size too.

## Open Questions

- **Per-project media schema.** Does `content.md` gain a new table column, an inline markdown image in the entity cell, per-project frontmatter, or a sidecar file, for images/video beyond the single global `photo:` key? Genuinely deferred — a content-model decision for the owner, not a design-system one. This change only builds the Figma-side convention (a named `project-image-fill` layer/slot with a grayscale Effect Style matching the hero photo pattern) so a future pull isn't guessing at unlabeled structure once the schema question is answered.
- **Content-surface differentiation.** Does Education belong on the public web table? Does MAILIN's synopsis live in a detail view not shown in the mobile table or the CV table? These are real, unresolved product decisions. This change documents the existing `{dev}`/`{drift}`-style marker precedent as the natural extension point (see Context) and builds a speculative "Project Detail" template on the Ideas page as a design exploration — but does not decide, or design-sync against, an answer that hasn't been made yet.
